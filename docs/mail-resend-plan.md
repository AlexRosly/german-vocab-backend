# ТЗ: переход Wortkarten с Gmail на домен и Resend

Статус: согласованное направление следующего почтового этапа; сейчас выбран Gmail SMTP. Собственный домен ещё не куплен, Resend не подключён. ТЗ не означает, что эти настройки уже сделаны.

## Цель

Отправлять восстановление пароля и подтверждение email от узнаваемого адреса Wortkarten, сохраняя пользовательские аккаунты, токены, сроки действия и интерфейс. Бизнес-логика работает через MailService и не обращается напрямую к Gmail/Resend. Смена драйвера не должна требовать миграции слов или прогресса.

## Предварительные условия

1. Владелец выбирает и регистрирует домен, получает доступ к DNS. Субдомены Netlify и хостинга VPS нельзя считать собственным почтовым доменом с доступом к его DNS.
2. Подключить домен или отдельный отправляющий поддомен в Resend; добавить конкретные SPF/DKIM-записи, выданные сервисом. Не создавать два отдельных SPF TXT на одном имени; изменения существующих записей согласовывать с текущей почтой.
3. Настроить DMARC и проверить выравнивание отправителя. Адрес ответов должен вести в реально читаемый ящик поддержки. Переход не требует менять адреса входа пользователей.
4. Требование владения/верификации — [официальная документация Resend](https://resend.com/docs/dashboard/domains/introduction). Доступные тарифы/лимиты и регион обработки повторно проверить перед подключением; не обещать бессрочную бесплатную рассылку.

## Изменения backend

- Добавить `MAIL_PROVIDER=resend` и отдельный адаптер MailTransport. Сохранить единый API MailService, существующие шаблоны и строгую валидацию одного получателя.
- Ключ Resend хранить только на VPS в приватном файле вне Git; предоставить минимально необходимые права отправки для выбранного домена. Новый провайдер не включать при отсутствии ключа/проверенного отправителя.
- Таймауты и безопасные коды ошибок, без адресов пользователей, кодов восстановления, API-ключей и SMTP/HTTP-ответов в логах. Корреляция по внутреннему ID события без содержимого письма.
- Не включать tracking открытий/кликов для писем авторизации и восстановления. Только сервер собирает ссылку с доверенным origin; не использовать Host/Referer клиента в ссылке.
- Для асинхронной очереди/outbox определить идемпотентность событий и политику повторов. Внешняя отправка не является частью транзакции PostgreSQL; нельзя подтверждать смену пароля/почты лишь по факту отправки.
- Подключать webhooks доставок только с проверкой подписи и повторов; публичный endpoint произвольной отправки не добавлять. Успешный HTTP/SMTP-ответ означает принятие письма, а не чтение пользователем.

## Процесс перехода

1. Добавить адаптер и тесты с подменой внешнего API, оставить Gmail доступным для отката.
2. Проверить домен/DNS, отправить явные тестовые письма в согласованные тестовые ящики разных провайдеров. Проверить Inbox/Spam, SPF/DKIM/DMARC и ссылки.
3. Указать Resend в конфигурации, проверить готовность до перезапуска, обновить только процесс wortkarten-api. Не рассылать письма всем существующим пользователям автоматически.
4. После приёмки обновить публичную политику конфиденциальности и сведения о почтовом обработчике; данные о стране/ответственном уточнить у владельца, не придумывать.
5. По окончании периода отката отозвать пароль приложения Gmail и удалить неиспользуемый секрет вручную. Не отзывать OAuth Google-входа или Google Drive резервных копий.

## Критерии готовности

- Смена провайдера не создаёт пользователей заново, не меняет роли, Google-привязки, словари, SRS или историю.
- Восстановление пароля и подтверждение email проверены на действительной/просроченной/повторной ссылке и после смены провайдера.
- Проверены отказы доставки, ограничения частоты, безопасные ответы для существующих/несуществующих email, повторные события и отсутствие секретов в логах.
- Gmail и Resend не отправляют одно событие одновременно. Есть явный порядок отката конфигурации без повторной массовой отправки.
- Документация отделяет mock-тесты, проверку настоящего отправителя и подтверждённое получение письма пользователем.
