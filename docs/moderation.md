# Административная модерация слов

Доступ к `/api/v1/moderation/words` требует действующий Bearer access token и
роль ADMIN в текущем серверном контексте. AuthGuard выполняется перед AdminGuard.
Сервис также проверяет роль на входе. Роль из заголовков, query или тела не
используется. Регистрация по-прежнему создаёт только USER; этот этап не добавляет
назначение администраторов и не меняет роли существующих пользователей.

| Метод | Путь после `/api/v1` | Назначение |
| --- | --- | --- |
| GET | /moderation/words | Очередь PENDING_REVIEW |
| GET | /moderation/words?status=REJECTED | Список с выбранным статусом |
| GET | /moderation/words/:id | Карточка, все переводы, примеры и revision |
| PATCH | /moderation/words/:id/status | Одобрение, отклонение или возврат на проверку |

Фильтр status принимает PENDING_REVIEW, PUBLISHED, REJECTED. Очередь возвращает
массив карточек от старых к новым. Детали карточки содержат revision — SHA-256
текущего содержимого, статуса, автора, переводов, примеров и времён изменения.
Ответы помечены Cache-Control: no-store. Личные словари и прогресс в детали
модерации не включаются.

Пример решения после GET карточки:

```json
{
  "publicationStatus": "PUBLISHED",
  "expectedRevision": "64-символьная revision из ответа GET"
}
```

Вместо PUBLISHED допустимы REJECTED и PENDING_REVIEW. expectedRevision обязателен:
64 строчных шестнадцатеричных символа. Лишние поля, включая role, userId,
createdByUserId, translation, отклоняются. Содержание администратор при необходимости
правит обычными маршрутами words/examples, затем открывает карточку заново.

## Сохранность данных и видимость

Решение обновляет только publicationStatus и служебный updatedAt общей записи Word.
Оно не создаёт копию слова и не меняет автора, UserWord, переводы, примеры,
WordProgress или StudySession. При одобрении слово появляется в библиотеке,
личная связь автора сохраняется. Другим пользователям слово не добавляется
автоматически — они используют отдельное добавление в свой словарь.

При отклонении карточка остаётся доступна автору для изучения. Чужие личные связи,
если слово было ранее опубликовано и добавлено другими пользователями, сохраняются,
но карточка скрывается из их активных словарей и обучения. Повторная публикация
возвращает её видимость без потери связей и прогресса. Собственные детали истории
при изменении видимости фильтруются правилами StudyService.

Автор может исправить REJECTED обычным PATCH /words/:id или изменить её примеры:
такое изменение снова переводит слово в PENDING_REVIEW. Опубликованную карточку
обычный пользователь редактировать не может. Включая администратора, создание
карточки через POST /words всегда даёт PENDING_REVIEW; публикация отдельная.

## Актуальность решения и дубликаты

Проверка revision и обновление выполняются в одной транзакции Serializable.
При конфликте P2034 транзакция повторяется до трёх попыток, с повторным чтением
карточки и проверкой revision. Изменения words/examples также обновляют родительский
Word в транзакции, поэтому одобрение не может успешно записаться поверх
конкурирующей авторской правки без новой проверки. Используется
[подход Prisma 6 к конкурентным транзакциям](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions).

Если карточка изменилась после просмотра, возвращается 409 с code=STALE_REVIEW.
Нужно открыть GET карточки заново и принять решение по актуальному содержимому.
Хеш учитывает сами поля, переводы и примеры, поэтому даже изменение в ту же
миллисекунду не остаётся незамеченным. Изменение статуса тоже меняет revision:
второй администратор со старой карточкой не перезапишет уже принятое решение.

Перед публикацией проверяются точные совпадения с PUBLISHED: написание без учёта
регистра, артикль, грамматическое число, русский перевод, множественная форма,
заметки. При совпадении возвращается 409 с code=DUPLICATE_WORD и wordId готовой
карточки; обе записи и личные связи сохраняются. Неоднозначные значения и разные
формы автоматически не объединяются. Перенос связей при объединении дубликатов
в этот этап не входит.

Повтор запроса со старой revision безопасно вернёт 409. Запрос того же статуса
с актуальной revision вернёт ту же карточку без повторной записи и изменения времени.

## Проверки

Из папки backend:

```powershell
npm run test:moderation
npm run test:auth
npm run test:words
npm run test:study
node node_modules/typescript/bin/tsc --noEmit --incremental false
npm run build
```

Тесты запускают реальные сервисы и HTTP через полный AppModule с подменой Prisma.
Проверяются USER/ADMIN, подмена роли, публикация и отклонение, сохранение словарей,
возврат на проверку, устаревшие решения, правки примеров/переводов, дубликаты,
повторные запросы и конфликты. Они не подтверждают реальную SQL-изоляцию:
конкурирующие решения и авторские правки нужно отдельно проверить на тестовой БД.

Prisma-схема, миграции и зависимости не меняются. Neon и роли в реальной БД этим
этапом не затрагиваются. Для реального входа необходима ранее подготовленная
миграция auth_sessions, применённая на тестовой ветке, и отдельный аккаунт с ADMIN.
Административный интерфейс frontend пока не реализован. Настройки языков и получение
переводов реализованы в backend: см. `docs/languages.md`. Следующий этап — frontend.
