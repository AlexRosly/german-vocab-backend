# Wortkarten — roadmap и контроль реализации

**Срез: 13.11.2026.** Основание: основное ТЗ v1.1, архитектурное дополнение v1.0, последующие решения владельца, текущие backend/frontend и отчёты проверок. Этот документ — актуальный рабочий план; прежние планы от 01–03.11 остаются историческими справками.

Основное ядро MVP реализовано. Следующий этап — довести удобство и эксплуатацию на новых хостингах, затем закрыть оставшиеся пользовательские функции. Проценты готовности не считаем: импорт, мобильная приёмка и ИИ имеют разный объём, поэтому «80% проекта» было бы неточной оценкой.

## Как читать и контролировать

| Статус | Значение |
| --- | --- |
| Реализовано | Код существует, относящиеся проверки пройдены. Это не автоматически подтверждение последней версии на публичном сайте. |
| Частично | Основа работает, но указанное расширение отсутствует. |
| Проверить на хостинге | Реализация готова; остаётся приёмка через реальный Netlify/VPS. |
| Не реализовано | Функция отсутствует в проверенных коде и модели данных. |
| Требует решения | Сначала согласовать поведение/источник/границы, затем реализовывать. |

Приоритеты: **P0** — сохранность данных и завершение выпуска; **P1** — удобство и готовность к новым пользователям; **P2** — развитие обучения и словаря; **P3** — последующие расширения. Это предлагаемый порядок работ, а не календарные обещания.

Redis, отдельная очередь задач, микросервисы и перевод в монорепозиторий не входят в обязательный ближайший план: в текущем ТЗ для них нет подтверждённой необходимости.

Отдельно остаётся продуктовое решение из дополнения: нужны ли несколько структурированных значений/переводов одного слова на одном языке и типы связей «синоним/антоним/управление». Сейчас у карточки одна текстовая запись перевода на язык, а разные смыслы могут храниться разными карточками; обычные кликабельные связи уже реализованы.

## 5. Как закрываем задачи

Один этап = один конкретный пользовательский результат. Перед началом выбираем ID и границы задачи. Для закрытия фиксируем:

1. Что изменилось и какой критерий из таблицы выполнен.
2. Какие проверки действительно прошли: автоматические, локальный браузер/mock, настоящая БД, публичный хостинг — с указанием уровня проверки.
3. Backend/frontend commit и факт push; обновление нужных сервисов.
4. Для изменения схемы — проверенная копия, согласованный SQL и отдельное согласие на рабочую миграцию.
5. Подтверждение работающего сценария на хостинге. До него запись может быть «код готов, приёмка ожидается».

После этого обновляем статус соответствующего ID и дату roadmap. Готовые Google-вход, обратные карточки, артикли, книги, массовое добавление и предложения исправлений не возвращаем в список отсутствующего. Тексты старых планов не переименовываем в актуальный статус без сверки.
