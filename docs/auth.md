# Базовая авторизация email/password

Этот этап добавляет самостоятельный AuthModule. Маршруты `words` и `examples`
теперь защищены и поддерживают личные словари: см. `docs/dictionaries.md`.
Маршруты `study` также защищены и персонализированы: см. `docs/study.md`.
Языковые настройки доступны отдельно: см. `docs/languages.md`.
Frontend интегрирован с авторизацией. Управление активными входами описано в
[account-sessions.md](account-sessions.md); локальные mock-проверки отделены от
проверки настоящего демо-сервера.

## Подготовка и проверки

Prisma и Prisma Client закреплены на 6.19.3. Добавлены bcrypt и Nest Throttler.

```powershell
npm install
npm run prisma:generate
npm run test:auth
node node_modules/typescript/bin/tsc --noEmit --incremental false
```

Четыре ошибки старого StudyService устранены на этапе персонального обучения.
Auth-тесты проверяют сервис с подменённым Prisma и HTTP через настоящий Nest-сервер;
они не подключаются к Neon и не подтверждают применение миграции в PostgreSQL.
`tsconfig.build.json` исключает тесты из сборки Nest и сохраняет точку входа
`dist/main.js`, которую использует `start:prod`.

Новая миграция `20261031120000_add_auth_sessions` только создаёт таблицу сессий,
уникальные ключи токенов и внешний ключ пользователя. Она не меняет старые слова,
переводы, прогресс, роли пользователей или предыдущие миграции.

Миграцию нужно отдельно проверить на тестовой ветке Neon. Команда после проверки
того, что DATABASE_URL указывает именно на тестовую ветку:

```powershell
npx prisma migrate deploy
npx prisma migrate status
```

Не применять к основной базе без отдельного подтверждения. Не запускать
`migrate reset`, `db push` или `migrate dev` для обхода существующих ошибок.

## API

Префикс `/api/v1/auth`:

| Метод | Путь | Данные | Результат |
| --- | --- | --- | --- |
| POST | /register | `{ email, password }` | 201: пользователь, access token, refresh cookie |
| POST | /login | `{ email, password }` | 200: пользователь, access token, refresh cookie |
| POST | /refresh | HttpOnly refresh cookie | 200: новый access token и новая refresh cookie |
| POST | /logout | HttpOnly refresh cookie | 204: сессия удалена, cookie очищена |
| GET | /sessions | Bearer | Свои активные входы без токенов и хешей |
| DELETE | /sessions/:id | Bearer | 204: завершить один свой вход |
| POST | /logout-all | Bearer | 204: завершить все свои входы |
| GET | /me | `Authorization: Bearer <accessToken>` | Текущий пользователь |

Email нормализуется в нижний регистр и очищается от пробелов по краям.
Пароль не обрезается: минимум 12 символов, максимум 72 байта UTF-8. bcrypt cost 12.
Регистрация всегда создаёт USER; роль, userId и прочие лишние поля DTO отклоняет.
Совпадение email с существующим пользователем не связывает аккаунты автоматически.
Подтверждение email, восстановление пароля и OAuth пока не реализованы.

Access token — случайный 256-битный непрозрачный токен на 10 минут, а не JWT.
Refresh token — отдельный случайный 256-битный токен на 7 дней с абсолютным сроком.
В `auth_sessions` хранятся SHA-256 хеши токенов. Обновление атомарно заменяет оба
токена; старые токены перестают работать. Параллельное обновление допускает только
одного победителя. При повторном использовании старого refresh возвращается 401;
отзыва всей цепочки сессий при обнаружении повторного использования пока нет.
Выход удаляет соответствующую сессию и сразу отзывает связанный access token.
Истёкшие сессии отклоняются; фоновая очистка истёкших записей пока не добавлена.

Cookie: `wortkarten_refresh`, HttpOnly, SameSite=Lax, Path=/api/v1/auth,
Secure при NODE_ENV=production. Параметры cookie не берутся из тела запроса.
Ответы авторизации имеют Cache-Control: no-store, refresh token не попадает в JSON.

## Подключение frontend на следующем этапе

Скопировать только нужные значения из `.env.auth.example` в существующий `.env`.
Не заменять существующий DATABASE_URL. FRONTEND_ORIGIN задаётся точным origin без
завершающего `/`. Для production нужны HTTPS и NODE_ENV=production. Cookie с
SameSite=Lax предполагает размещение API и frontend на одном site (например,
app.example.com и api.example.com); для разных site нужна отдельная настройка.

Браузерные POST к auth разрешены только с FRONTEND_ORIGIN. Из Swagger на другом
origin такие запросы будут отклонены; использовать frontend или небраузерный клиент.
Клиенты без Origin, например curl, разрешены. Cookies требуют `credentials: "include"`.
Access token следует хранить в памяти, обновлять через /refresh и передавать как Bearer.
Refresh-запросы на клиенте нужно объединять, чтобы вкладка не обновляла одну сессию параллельно.

AuthGuard и @CurrentUser экспортируются для последующей адаптации контроллеров.
Пользователь получается из записи сессии в БД; userId из тела/параметров не используется.
Роль читается из User при проверке access token, не из клиентского запроса.

Ограничение: 10 регистраций/входов в минуту на IP и маршрут, 30 обновлений/выходов.
Хранилище лимитов локально одному процессу. Для нескольких экземпляров нужен общий
storage; за reverse proxy необходимо отдельно настроить доверие только известным proxy,
иначе все клиенты могут разделять один лимит. Заголовку X-Forwarded-For вслепую не доверяем.

## Проверка на тестовой БД после применения миграции

1. Зарегистрировать два разных аккаунта: оба USER, id различаются.
2. Войти повторно и убедиться, что /me возвращает пользователя именно этого токена.
3. Обновить сессию: старые access и refresh должны вернуть 401.
4. Выйти: новый access этой сессии должен вернуть 401; другая сессия продолжает работать.
5. Проверить неверный пароль, повторную регистрацию, лишние поля role/userId и лимит входа.
6. Проверки изоляции слов и обучения выполнить после следующего этапа их адаптации.
