# german-vocab-backend

Backend-репозиторий: NestJS + PostgreSQL + Prisma + REST/OpenAPI.

## Текущий статус — 09.11.2026

Реализованы авторизация email/Google, USER/ADMIN, личный словарь и общая библиотека, мультиязычные слова и примеры, модерация и предложения исправлений, персональные тренировки/SRS/история, личные материалы, книги и массовое добавление из библиотеки. Рабочая схема содержит 18 таблиц и 15 миграций; последнее применение проверено 09.11.2026.

**[Roadmap: что готово, что осталось и как принимаем результат](docs/roadmap.md)**.

Основной backend размещён на VPS по сообщению владельца; БД — Neon. Выпуск последней функции на фактических хостах отмечается отдельно от готовности кода. Инструкции: [VPS](docs/vps-deployment.md), [предложения исправлений](docs/correction-suggestions.md), [резервные копии](docs/database-backups.md). Подготовлена [автоматизация Google Drive](docs/automatic-backups.md) с отдельной приёмкой настройки на VPS.



## Памятка: что требуется для внедрения FSRS

**Составлено 26.11.2026. Статус: план будущего улучшения, не реализация.** Владелец принял режимы множественного числа и написания и решил сохранить текущий алгоритм. FSRS, его зависимости и миграции пока не добавлены; эта памятка не разрешает менять рабочее расписание. Принятый этап «Обучение» не открывается заново из-за этой идеи.

### 1. Что работает сейчас

В [StudyService](src/study/study.service.ts) `KNOWN` увеличивает серию и назначает интервалы 1 → 3 → 7 → 14 → 30 дней; после пятого успешного ответа интервал остаётся 30 дней. `NEEDS_REVIEW` сбрасывает серию и назначает повтор через день. Ранний ответ также влияет на серию.

Персональный `WordProgress` хранится по паре пользователь/слово и общий для всех режимов. В [схеме Prisma](prisma/schema.prisma) и [DTO занятия](src/study/dto/create-study-session.dto.ts) есть две оценки. Сессия сохраняется порцией до 500 разных слов с защитой `Idempotency-Key`; время `answeredAt` сейчас задаётся сервером при сохранении всей порции. Снимок `StudySessionWord.nextReviewAt` хранит назначенный тогда срок; у старых записей срок и режим могут быть неизвестны. Контракты: [обучение](docs/study.md), [история](docs/study-history-metadata.md).

### 2. Какие решения согласовать до разработки

- **Оценки:** начать с двух кнопок: «Нужно повторить» → `Again`, «Знаю» → `Good`. Это предлагаемое соответствие; `Hard` и `Easy` из старой истории не выводить. Четыре кнопки возможны отдельно. Забытый ответ всегда соответствует `Again`, а не `Hard`.
- **Единица прогресса:** для первого выпуска предлагается сохранить одну модель памяти на пользователь/слово. Раздельные состояния для перевода, артиклей, написания и множественного числа — другое продуктовое решение; их нельзя получить простым разделением существующего общего прогресса.
- **Расписание:** выбрать целевую вероятность вспоминания, например 90%, максимальный интервал и шаги переобучения. 90% — отправная настройка, не гарантия результата. Более высокая цель увеличивает нагрузку. Мягкий дневной план новых слов остаётся самостоятельной настройкой.
- **Повторные попытки:** определить, какие ответы меняют расписание: плановые, ранние, свободная тренировка, повтор ошибок в тот же день. Зафиксировать порядок нескольких ответов по одному слову и правила коротких интервалов; не считать каждое нажатие независимым успешным повторением по умолчанию.
- **Включение:** сначала отдельный тестовый профиль, затем добровольное включение для пользователя. Предлагается сохранять текущие сроки при переходе и рассчитывать новый срок после следующего ответа; массовый пересчёт всех дат не включать автоматически.

### 3. Библиотека и окружение

Кандидат для NestJS/TypeScript — [ts-fsrs](https://github.com/open-spaced-repetition/ts-fsrs). Перед разработкой проверить релиз, лицензию, API, поддержку, точную версию модели и требования среды; закрепить выбранную версию пакета и lockfile. Версия библиотеки и версия модели FSRS — разные вещи, обе должны быть воспроизводимы.

На дату проверки актуальная документация `ts-fsrs` v6 требует Node.js ≥24 и описывает новый API; старые примеры `fsrs()`/`createEmptyCard()` нельзя смешивать с ним. Сейчас README проекта указывает Node.js 20+, поэтому фактические `node --version` на VPS, CI и локальном стенде нужно проверить отдельно. Возможный переход на Node.js 24 проверяется совместно с NestJS, Prisma, PM2 и остальными зависимостями; эта памятка среду не обновляет. Если выбирается другая поддерживаемая версия библиотеки, её совместимость и модель проверяются явно. [Актуальная установка](https://open-spaced-repetition.github.io/ts-fsrs/guide/quick-start).

Расчёт расписания и обучение персональных параметров — разные задачи. Первый выпуск можно делать со стандартными параметрами выбранной модели. Оптимизатор и персональная подстройка по накопленной истории — следующий необязательный этап; внешние API, ИИ-сервис и передача истории третьим лицам для базового планировщика не требуются.

### 4. Что добавить в данные

Точная схема определяется после выбора версии модели. Предлагается добавочное хранение, без удаления прежнего прогресса и истории:

| Данные | Что требуется |
| --- | --- |
| Личные настройки | Активный алгоритм, модель/версия параметров, целевое удержание, ограничения интервалов и дата включения. |
| Состояние карточки | Уникальная пара `userId + wordId`, состояние обучения, последняя дата ответа, следующий срок, счётчики повторов/забываний, модель памяти выбранной версии. Например, stability/difficulty; дополнительные компоненты новых моделей сохраняются по их контракту. Нужны версия записи и индекс очереди `userId + dueAt`. |
| Журнал ответов | Уникальный ID события, владелец, слово, режим, оценка, время ответа и получения сервером, предыдущий/назначенный срок, версия алгоритма/параметров, состояние до/после или достаточные данные для воспроизведения. Отмечать источник инициализации и качество старых временных меток. |
| Переход и откат | Снимок исходного legacy-прогресса и дат, версия процедуры переноса, результат проверки и указатель активного алгоритма. |

`retrievability` — оценка на конкретный момент времени; её можно вычислять при необходимости, а не хранить как постоянное свойство карточки. Структуру памяти валидировать по выбранной модели, не переносить старые колонки в новую модель только по похожим названиям.

### 5. История и безопасная инициализация

Существующая история полезна, но не является полным FSRS-журналом. Старые оценки только бинарные, `answeredAt` соответствует сохранению порции, а часть режимов/сроков отсутствует. Нельзя выдумывать точное время попытки, `Hard/Easy` или прежние даты и выдавать их за наблюдения.

На восстановленной копии сравнить два варианта: воспроизвести пригодную историю с явным преобразованием `KNOWN→Good`, `NEEDS_REVIEW→Again` и отметкой приблизительных данных либо начать новое состояние FSRS с момента включения, сохранив старую историю и текущий срок. Выбрать и документировать один вариант. При неполной истории не обещать точную персонализацию; стандартные параметры позволяют начать без предварительного обучения оптимизатора. Перенос нашей фиксированной лестницы — отдельная процедура, не готовая миграция между версиями FSRS. [Ограничения и версионирование переноса](https://open-spaced-repetition.github.io/ts-fsrs/guide/migration).

### 6. Backend, API и frontend

- Выделить серверный адаптер планировщика; клиент передаёт ответ, но не авторитетное состояние памяти, интервал или пользовательский ID. Проверки личного словаря и изоляция пользователей сохраняются.
- Добавить оценку/версию протокола и стабильный ID события. Если сохраняем время попытки с клиента, проверять допустимый диапазон, порядок и расхождение часов, отдельно сохраняя время приёма сервером. Старые метки остаются как есть.
- Состояние, событие и история занятия меняются атомарно. Повтор запроса, конфликт двух устройств или повторная отправка порции не должны дважды продвигать карточку. Нынешнее сравнение `Idempotency-Key` нужно расширить на новые значимые поля, сохранив прежний контракт старых запросов.
- Определить совместимость старого клиента: legacy-пользователь продолжает прежнюю схему; для FSRS-пользователя старый протокол либо явно преобразуется по согласованным правилам, либо отклоняется с предложением обновить страницу. Нельзя незаметно применить legacy-расчёт к активному FSRS-состоянию.
- Очередь `/study/due`, режимы, история, статистика и CSV должны читать выбранный алгоритм. Снимки исторических сроков не переписывать текущим `dueAt`. Не восстанавливать полное состояние памяти из CSV словаря: он не содержит всего журнала обучения.
- В интерфейсе сохранить согласованные две кнопки либо отдельно реализовать четыре, показать назначенный срок и понятное описание новой настройки. Интервалы меньше суток отображать корректно; формы, клавиатура и очередь должны работать на iPhone.

### 7. Порядок внедрения и критерии готовности

1. Согласовать решения из пункта 2, проверить окружение и выбрать библиотеку/модель. Реализовать изолированный адаптер с фиксированными временем и параметрами в тестах.
2. Подготовить добавочную миграцию, журнал событий и процедуру инициализации. Проверить их на свежей восстановленной копии: прежние таблицы, строки и история сохраняются.
3. Запустить сравнительный расчёт без влияния на рабочие даты: оценить очереди, нагрузку, забытые/новые/просроченные слова и повторные попытки в день.
4. Проверить новые оценки, минуты/сутки и UTC/Europe/Berlin с переходами времени, длинные занятия и повторы запросов, параллельные устройства, частичные сбои, старый клиент, архивирование/восстановление и повторное добавление слова. Чужие личные данные недоступны, включая ADMIN.
5. Проверить перенос и откат целиком. Одного выключения флага недостаточно: старые снимки могут уже не отражать новые ответы. Откат должен сохранять новые события и возвращать согласованное состояние/даты без дублирования статистики; аварийное восстановление копии — отдельный сценарий.
6. После профильных и регрессионных проверок подготовить выпуск и свежую резервную копию. Миграция основной Neon — только после отдельного согласия владельца по [AGENTS.md](AGENTS.md). Сначала совместимый backend на VPS, затем frontend на Netlify; включение ограничить тестовым профилем и принять реальный цикл с сохранением после перезагрузки.
7. Включать остальных пользователей постепенно, контролируя ошибки, длительность сохранения и изменение количества назначенных повторов. Смена версии модели или параметров в будущем также требует проверенного сценария, без неожиданного пересчёта всей очереди.

**Минимальный результат:** воспроизводимый расчёт выбранной FSRS-модели, персональное состояние и журнал, безопасная совместимость с существующим обучением, принятый перенос/откат и проверенный пользовательский сценарий. Автооптимизация параметров и четыре кнопки не являются обязательным условием первого выпуска.

- Node.js 20.9+ (для VPS рекомендуется Node 22)

## Запуск локально

```bash
cp .env.example .env
npm install
docker compose up -d postgres
npm run prisma:generate
npm run prisma:migrate -- --name init
npm run start:dev
```

API: http://localhost:3001/api/v1  
Swagger: http://localhost:3001/docs  
Health: http://localhost:3001/api/v1/health
